# Mockingbird — Full-Project Audit (2026-08-24)

## Why this exists

Triggered by user request after two concrete defects surfaced in manual review:

1. **Multi-file upload is not supported.** Real SV teams have many input files
   (.txt/.json/.xml) representing many services. Today the pipeline is
   hard-coded 1 file → 1 stub, end to end from the portal dropzone through
   `ingestion-service`. The data model (`Project` 1→N `Stub`) already
   supports the target shape; the gap is entirely in the upload layer.
   See PART 1 finding in the session that produced this doc.
2. **"Reports" menu appears missing.** Root cause: there is no top-level
   Reports nav item/page in the portal at all — only a report tab buried
   inside a single deployment's detail page. This is not environment-specific
   (not a "broke when copied to another machine" bug); it behaves identically
   anywhere.

Both of the above are being designed/fixed separately (tracked as a plan,
not part of this audit). This audit's job is to find what ELSE is wrong —
the two known defects above are proof the "Phase X ✅ COMPLETE" status
claims in START_HERE.md/CLAUDE.md are not a reliable signal of feature
completeness, only of "code exists." Trust nothing without checking it.

## Ground rules for every agent below

- **Read-only investigation only.** Do not edit code. Do not run destructive
  commands. If you need to run something to observe behavior (tests,
  Playwright, a service), that's fine — editing source files is not.
- Cite every finding as `file:line`. A finding without a citation doesn't
  ship.
- Distinguish **CONFIRMED** (you read the code/ran it and verified the
  defect) from **SUSPECTED** (looks wrong, didn't verify) — don't blur these.
- Ignore cosmetic/style nits. We want correctness bugs, broken flows,
  security gaps, and claims-vs-reality mismatches (docs or status tables
  claiming something works that doesn't).
- Report back in your final message — under 600 words, most severe first.

## Workstreams (each an independent agent — no shared state)

### A — Python backend services correctness
Scope: `services/project-service`, `services/ingestion-service`,
`services/parser-worker`, `services/generator-worker`,
`services/deployer-worker`, `services/metrics-service`,
`services/reporter-service`, `services/ai-service`.
Look for: inverted conditions, swallowed exceptions, RFC 7807 error-shape
violations (per CLAUDE.md coding conventions), SQL/path-traversal risk in
file handling, race conditions in SQS consumers, and any code path where a
"complete" feature actually silently no-ops or returns fabricated success.

### B — Node services + security
Scope: `services/auth-service`, `services/notification-service`.
Look for: JWT/LDAP auth bypass paths, RBAC gaps (routes missing role
checks), secret handling (anything not going through Vault per CLAUDE.md
rule), and injection risks in the notification channels (email/Slack/Teams
webhook payload construction). Also verify: does the `fast-jwt` critical
CVE (GHSA-gm45-q3v2-6cf8 etc., surfaced via `@fastify/jwt@8.x` →
`fast-jwt@<=6.2.3`) have a real exploitable path in how `auth-service` uses
`@fastify/jwt` (check `src/plugins/jwt.ts` and how tokens are issued/verified)?
Same question for `nodemailer@<=9.0.0`'s SMTP-injection/SSRF advisories
against `src/channels/email.ts`.

### C — Portal frontend correctness
Scope: `portal/src/`. Look for: routes reachable without the RBAC check
their content implies, pages that call an API endpoint that doesn't exist
or has a mismatched contract (compare `portal/src/api/*.ts` against the
actual FastAPI/Fastify route signatures), broken error states (silent
failures, unhandled promise rejections), and any other "menu item/feature
that looks wired up but isn't" in the same shape as the Reports gap.

### D — Run the existing Playwright suite and report reality
Scope: `portal/e2e/*.spec.ts` (mocked-API suite — no backend required).
Actually run it (`cd portal && npx playwright test`), not just read it.
Report pass/fail per spec, and for any failure include the actual error
output. If the mocked suite is green, additionally attempt
`portal/e2e/real/*.spec.ts` against locally started services
(`scripts/start-services.ps1`) and report whether that's even runnable
in this environment (missing env vars, LDAP/Vault dependencies that can't
be satisfied locally, etc.) — this directly answers whether "use Playwright
and test the app completely" is something that already works today or is
blocked on environment setup.

### E — Docs-vs-code consistency sweep
Scope: every `*.md` in the repo root and `docs/`, cross-checked against
`services/`, `portal/`, `terraform/`. For every claim of the form "X is
built / complete / supported," verify it against actual code. This is the
same check already done for CLAUDE.md's Phase Reference table (which was
found stale) — repeat that method across the rest of the documentation set.
Flag every doc claim that doesn't hold up, with the specific line making
the claim and the code (or absence of code) that contradicts it.

## After all five land

A follow-up integration pass reconciles overlapping findings (e.g., if both
A and C flag the same upload contract mismatch from different sides) and
produces one prioritized punch list. That pass is done by the orchestrating
session, not a separate agent.
