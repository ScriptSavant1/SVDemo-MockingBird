Mockingbird — Architecture Reference

A single source of truth for how the platform is actually built — not how it was originally planned. Every diagram below is a real read of the codebase, and every status tag (BUILT PARTIAL NOT BUILT) reflects what currently runs, not what was decided.

What Mockingbird does, in one paragraph: a project team uploads their API spec (raw HTTP request/response pairs, Postman collections, or OpenAPI) in any supported format. Mockingbird auto-detects the format, parses it, and generates a self-contained Spring Boot + WireMock stub project. That project can be downloaded and run locally for testing, or deployed automatically to an EC2 instance where it serves 10,000+ requests/second. When the project is finished, the EC2 instance is terminated to save cost — but the stub definition stays in PostgreSQL and S3, so redeploying later takes about 4 minutes with no re-upload.

System architecture

The platform splits into a synchronous request path (portal ↔ API services) and an asynchronous work path (SQS-driven background workers). Nothing in the async path blocks a user — uploading a file returns immediately; parsing, generation, and deployment happen in the background and are tracked as polled Job records.

Upload → deploy pipeline

This is the mechanism behind the product's core promise — upload files, get running stubs. Everything from upload through "ready to download" runs with zero manual steps. The one deliberate manual gate is Deploy: provisioning a billable EC2 instance is a decision a person makes, not something that fires automatically the instant a file lands.

Batch upload (added this session): multiple files can be uploaded in one action — each becomes an independent stub with its own row in the pipeline above, running in parallel through the same automatic top row. A failure on one file doesn't block the others.

Authentication model

This is the part that causes the most confusion, because "auth" here is actually three unrelated mechanisms that happen to share the word. None of them overlap.

Practical risk worth raising with your infra/security team before more work goes into on-prem SSH: a Python worker holding its own SSH key and connecting directly into the on-prem estate from AWS is a pattern many bank security teams reject outright — they typically require a privileged-access-management flow (jump host, session-recorded bastion) instead. Confirm this is acceptable before building it out.

Deployment targets — documented vs. real
