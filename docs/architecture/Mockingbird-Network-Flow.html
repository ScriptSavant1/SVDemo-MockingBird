Mockingbird — network flow

Which machine talks to which, and in what order — from a team signing in, through building and provisioning a stub, to applications and load generators sending test traffic to it.

The flow, step by step

  1. 1Use the portal. The browser loads the React portal from Nginx, which routes every /api/v1 call to the right service. Live TPS arrives over a WebSocket.
  2. 2Sign in. The auth service checks the user against LDAP / Active Directory and maps their group to a role (admin, SV team, owner, viewer).
  3. 3Upload a spec. The ingestion service stores the file in S3 and puts a parse job on an SQS queue.
  4. 4Parse, generate, build. Workers take jobs from SQS in turn. The deployer starts a GitLab CI pipeline where Kaniko builds the stub image from Artifactory dependencies.
  5. 5Provision. The deployer runs Terraform to create the project's EC2, which pulls the image and starts the stub. The team gets a URL and API key.
  6. 6Test. Applications under test and load generators call the stub on HTTPS 443 (mutual TLS optional), never the real dependency.
  7. 7Monitor. The metrics service scrapes each stub every 30 seconds into Timestream and pushes live figures to the portal.
  8. 8AI and alerts. The AI service asks Claude to draft specs; the notification service posts to email, Slack and Teams.
