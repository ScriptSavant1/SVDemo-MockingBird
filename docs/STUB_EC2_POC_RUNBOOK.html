Mockingbird Stub — EC2 POC Setup & Operations Runbook

Standalone guide for running the Mockingbird stub as a plain JAR + systemd service on a RHEL9/RHEL10 EC2 box — an alternative to the Terraform/Docker auto-deploy path in terraform/stub-ec2/, for teams doing a manual EC2 proof-of-concept. Independent of any load-generator pipeline — it's a standalone Spring Boot jar run on its own EC2 instance.

All bucket/file/region values below are placeholders. Edit the top of scripts/deploy-stub-ec2.sh with your real S3 bucket, object keys, and region before running it — the script itself refuses to run until every CHANGE_ME value has been replaced.
No HTTPS/mTLS on this path (yet). This script deploys a plain JAR — TLS termination (nginx in front of the stub) is only wired into the Docker image built by the Terraform auto-deploy path. A stub deployed with this script always serves plain HTTP on 8080. See STUB_HTTPS_MTLS_DESIGN.md if you need HTTPS and can use that path instead.
  • Install script: scripts/deploy-stub-ec2.sh
  • Platform: RHEL9 / RHEL10 EC2 instance
  • App API port: 8080  |  Management/health port: 8081
  • S3 bucket: <your-s3-bucket> (edit in the script — placeholder in this doc)
  • Install locations: Java /opt/corretto-21, app /opt/mockingbird-stub/app.jar
  • Service name: mockingbird-stub (systemd), runs as the dedicated mockingbird user — not root

1. What the install script does

scripts/deploy-stub-ec2.sh (run as root) performs, in order:

  1. Confirms it is running as root, and that every placeholder value (bucket, file keys, region) has actually been edited.
  2. Patches the OS with dnf update -y (CVE remediation). Skip with SKIP_OS_UPDATE=1 — useful in PROD where patching needs a change window, or on a redeploy where the box was already patched on first install (see §6). A kernel update only takes effect after a reboot — plan one on first install.
  3. Creates a dedicated, unprivileged mockingbird system user — the stub runs as this user, never as root.
  4. Resolves the AWS CLI; if missing, installs it automatically.
  5. Preflight: verifies AWS credentials (instance IAM role) and that both S3 objects exist.
  6. Auto-sizes the JVM heap to ~50% of system RAM (cap 24g, min 1g). Override with MOCK_XMX, e.g. MOCK_XMX=8g sudo -E ./scripts/deploy-stub-ec2.sh.
  7. Applies kernel tuning for high TPS (/etc/sysctl.d/99-mockingbird-stub.conf): widened ephemeral port range, tcp_tw_reuse, and somaxconn=4096 (to match WireMock's accept queue). Needed to sustain multi-thousand TPS without accept-queue drops or socket exhaustion.
  8. Downloads + installs Java to /opt/corretto-21, exports JAVA_HOME system-wide.
  9. Downloads the app jar to /opt/mockingbird-stub/app.jar, owned by the mockingbird user.
  10. Opens stub port 8080/tcp in firewalld (if firewalld is active). 8081 (actuator) is left closed to the world — open it to a monitoring range only via OPEN_ACTUATOR_CIDR=<cidr>. Without this step the load generator gets no route to host even when the security group allows 8080 (a host firewall silently rejects it).
  11. Creates a systemd service mockingbird-stub that:
    • runs as the unprivileged mockingbird user, not root,
    • starts on boot (WantedBy=multi-user.target),
    • restarts on failure (Restart=on-failure),
    • raises the open-file-descriptor limit (LimitNOFILE=1048576) for high TPS,
    • runs the JVM with G1GC low-pause flags.
  12. Starts the service and verifies it is active (dumps logs and fails if not).

Prerequisites

  • The instance has an IAM instance profile with S3 read access to your bucket. (The script fails early with a clear message if not.)
  • Network/proxy access to install the AWS CLI (only needed the first time).

2. First-time install (detailed steps)

Do NOT create/run the script from /etc. Use /opt or your home directory.
# 1. Copy scripts/deploy-stub-ec2.sh onto the box (scp, or paste via vi)
cd /opt
sudo vi deploy-stub-ec2.sh      # paste the script content, save & quit (:wq)

# 2. Edit the placeholder values at the top of the script
sudo vi deploy-stub-ec2.sh      # BUCKET, JAVA_FILE, JAR_FILE, REGION

# 3. Make it executable
sudo chmod +x deploy-stub-ec2.sh

# 4. Run it as root
sudo ./deploy-stub-ec2.sh

Expected successful output (tail)

[..] Service mockingbird-stub is running (as user 'mockingbird').
[..] Done.
  Health:   curl http://localhost:8081/actuator/health

Verify the install

systemctl status mockingbird-stub --no-pager      # active (running)
sudo ss -tlnp | grep java                          # listening on 8080 and 8081
curl -s http://localhost:8081/actuator/health      # {"status":"UP"}

3. Network — the load generator must clear THREE layers to reach the stub

Reaching the stub on 8080 from the load generator (LG) requires all three of these to allow it. Missing any one produces a different symptom (see the table). This is the single most common cause of "works from a local test client, fails from the AWS LG".

LayerWhereSymptom if it blocks 8080
1. Security Group (stateful)Stub EC2's SG, inboundcontext deadline exceeded (silent drop → timeout)
2. NACL (stateless)Stub subnet's NACL, in + outno route to host (fast reject)
3. Host firewall (firewalld)On the stub OS itselfno route to host (ICMP admin-prohibited)

3a. Security Group (survives stop/start — one-time)

Inbound rule on the stub instance's SG:

PortPurposeSource (recommended)
8080Application APILG security group, or subnet CIDR (e.g. 10.0.1.0/24 — use your own subnet's actual range)
8081Health/management(optional) monitoring range only, if scraped remotely

Scope the source to the whole LG subnet CIDR, not a single IP — on-demand LGs get a new IP each provision. A /32 rule breaks on the next run.

3b. NACL (stateless — needs BOTH directions)

If the stub and LG are in different subnets, the stub subnet's NACL must allow:

  • Inbound: TCP 8080 from the LG CIDR
  • Outbound: TCP ephemeral 1024-65535 back to the LG CIDR (return traffic)

Give the allow rules a lower rule number than any deny. (If both hosts share one subnet, the NACL isn't in the path.)

3c. Host firewall (firewalld on the stub)

RHEL9/10 runs firewalld by default, allowing only SSH. 8080 must be opened on the host, or the LG gets no route to host even when the SG and NACL are correct. The install script does this automatically. To do it manually:

sudo firewall-cmd --permanent --add-port=8080/tcp
sudo firewall-cmd --reload
sudo firewall-cmd --list-ports              # confirm 8080/tcp
Security-group rules survive stop/start. The firewalld rule is baked into the host by the install script, so it persists too — but a freshly-provisioned host that did NOT run the install script will not have it. Always run the install script (or open 8080) on every new stub host.

Prove reachability from the LG (before running a real test)

Run on the LG instance:

# Health probe
curl -v http://<mockingbird-private-ip>:8081/actuator/health

# API probe — replace with a real path/method/body from this stub's own
# generated setup guide (STUB_ENGINE_SETUP_GUIDE.html), not this example
curl -v http://<mockingbird-private-ip>:8080/api/v1/example-endpoint \
  -H "Content-Type: application/json" --data-binary @/tmp/payload.json

If these connect from the LG, your load-test tool will connect too.

4. Weekend shutdown (save cost) & Monday restart

Cost summary

  • Stopping the instance stops the compute charge (the main cost).
  • You still pay a small EBS storage charge while stopped (negligible for a weekend — a ~50 GB gp3 volume is a few dollars/month, i.e. pennies for 2 days).
  • An Elastic IP (if attached) incurs a small idle fee while the instance is stopped. If the instance uses an auto-assigned IP (no EIP), there is no such fee.

Verdict: stopping over the weekend is worthwhile and safe.

To stop (Friday)

Stop the instance from the AWS console (EC2 → Instances → Instance state → Stop), or via CLI. Stop the LG instance too if it is running.

On restart (Monday) — the jar auto-starts

Because mockingbird-stub is a systemd service enabled at boot, you do NOT need to re-run the script or restart the jar manually. It comes up automatically.

IMPORTANT: a stop/start usually assigns a new private IP. Re-check it.

Monday checklist (run on the mockingbird box after it boots):

# 1. New private IP (update your LG/load-test host with this)
hostname -I | awk '{print $1}'

# 2. Confirm the service auto-started
systemctl status mockingbird-stub --no-pager      # 8080 + 8081 present
sudo ss -tlnp | grep java
curl -s http://localhost:8081/actuator/health      # {"status":"UP"}

One-liner status check:

echo "IP: $(hostname -I | awk '{print $1}')"; systemctl is-active mockingbird-stub; sudo ss -tlnp | grep java

If you also stopped the LG, its IP changes too — re-add/verify it in your load-test tool with the new address, and re-point the host parameter.

5. Load-test script configuration

Example API request (recorded against localhost, which must be replaced):

POST http://<mockingbird-private-ip>:8080/api/v1/example-endpoint
Content-Type: application/json

{ "...": "..." }

Key points

  • Host: use the mockingbird private IP, NOT localhost. localhost on the LG points at the LG itself.
  • Port: 8080 (application API). 8081 is health only.
  • Parameterize the host: define a parameter (e.g. HOST / {MockHost}) so a new IP after stop/start or redeploy needs a one-line change, not a re-record/re-zip. avoids the stale-IP trap
  • Parameterize request data: vary per-iteration fields for realistic load.
  • Validate responses: check response status/body so failures (e.g. 404 "Request was not matched") are caught during the run.
LoadRunner DevWeb note: the generated script builds its URL from load.config.user.args["HOST"] and ["PORT"]. When uploading to LRE, include the whole script folder (with the body/data files) — "runtime files only" can cause no such file or directory on the LG.

6. Service management (day-to-day)

# Status / logs
systemctl status mockingbird-stub --no-pager
journalctl -u mockingbird-stub -f                  # live logs
journalctl -u mockingbird-stub -n 100 --no-pager

# Start / stop / restart
sudo systemctl start   mockingbird-stub
sudo systemctl stop    mockingbird-stub
sudo systemctl restart mockingbird-stub

# Disable / enable auto-start on boot
sudo systemctl disable mockingbird-stub
sudo systemctl enable  mockingbird-stub

A genuinely stopped stub must refuse new connections — curl should return Connection refused, never a normal HTTP response. If you stop it and still get a response, something else is still listening: check sudo ss -tlnp | grep -E ':8080|:8081' for a leftover process, and confirm you're testing the right host/IP.

Redeploy a new jar

  1. Upload the new jar to your S3 bucket, under the same key the script is configured to use (JAR_FILE).
  2. Re-run the script. For a fast redeploy that skips re-patching the OS (already done on first install): 
    SKIP_OS_UPDATE=1 sudo -E ./deploy-stub-ec2.sh

Change the heap size

MOCK_XMX=8g sudo -E ./deploy-stub-ec2.sh    # note: sudo -E to pass the var

(The -E preserves the MOCK_XMX environment variable through sudo.)

7. Scaling to 10,000+ TPS

The stub application is already tuned for high TPS (Jetty acceptors = vCPU count, async response threads, request journal disabled, G1GC low-pause, Java 21 virtual threads). At 10K TPS the limits you hit are almost always the host and the load generator, not the stub code.

Stub host (done by the install script)

  • File descriptors: LimitNOFILE=1048576 in the systemd unit. Default 1024 chokes at high TPS (every socket is an FD).
  • Kernel tuning: /etc/sysctl.d/99-mockingbird-stub.conf — ephemeral port range, tcp_tw_reuse, somaxconn=4096 (≥ WireMock's accept queue of 1000).
  • Instance size: c6i.2xlarge (8 vCPU / 16 GB) sustains ~12-18K TPS for REST. Heap auto-sizes to ~50% RAM (~8g on 16 GB) — leave headroom for Jetty/OS.

Load generator (NOT the stub — but the usual real bottleneck)

  • Enable HTTP keep-alive / connection reuse. Without it the LG opens a new TCP connection (and burns a source port) per request — cannot assign requested address after a few minutes at high TPS. Set a non-zero keep-alive timeout and a small max-connections-per-server in the LG runtime settings.
  • Prefer clean HTTP/1.1 keep-alive over HTTP/2 cleartext against WireMock (h2c fallback can churn connections).
  • Use multiple LGs. A single LG typically cannot generate a clean 10K TPS; plan 2-3 LGs and split the load.
  • Widen ephemeral ports on the LG too (net.ipv4.ip_local_port_range, tcp_tw_reuse) — same tuning as the stub host.

How to confirm where the ceiling is

# On the stub host, during a run:
sudo ss -s                                    # total sockets / TIME-WAIT count
sudo ss -tan | grep -c ':8080'                # active connections to the stub
journalctl -u mockingbird-stub -f             # any errors / GC pauses?
watch -n1 'sudo ss -tan | grep TIME-WAIT | wc -l'   # TIME_WAIT climbing = no reuse

If TIME_WAIT climbs into the tens of thousands, connection reuse isn't happening — fix keep-alive on the LG before blaming the stub.
