## BUG-034 — Upload handler round-tripped every generated project file through a real temp directory

| Field | Value |
|-------|-------|
| **ID** | BUG-034 |
| **Found** | 2026-08-27 |
| **Status** | FIXED |
| **Severity** | Medium (performance) |
| **File** | `services/ingestion-service/src/ingestion_service/routers/upload.py`, `services/parser-worker/src/parser_worker/generator/springboot.py` |
| **Commit** | (session fix) |

**Description:**
Reported as "creating a stub takes ~40 seconds after uploading." The upload handler's step 8 (pre-generating the full Spring Boot project for local dev) wrote every generated file — Java sources, `pom.xml`, the setup guide HTML, every WireMock mapping/lookup-table JSON — to a real temp directory, then walked it with `Path.rglob("*")` to build a ZIP, then `shutil.rmtree`'d the directory. Real disk I/O for every one of potentially hundreds of generated files, on every single upload, purely to immediately re-read and discard them — a likely contributor on a machine with real-time antivirus/EDR scanning each new file.

**Root cause:**
`generate_springboot_project` only ever wrote to a real `Path`. There was no way to get the generated project as bytes without going through the filesystem.

**Fix:**
Refactored `generator/springboot.py` around one in-memory builder, `build_springboot_project_files(parsed, project_id, project_name) -> dict[str, bytes]`. `generate_springboot_project` (disk) and a new `generate_springboot_project_zip` (ZIP bytes, no filesystem writes beyond reading the read-only bundled templates) are both thin wrappers around it. `upload.py` now calls `generate_springboot_project_zip` directly — no temp directory, no `rglob`, no `shutil.rmtree`. Same pattern applied to `generator/wiremock.py` (`build_wiremock_mapping_files`) and `generator/lookup_table.py` (`build_lookup_table_files`).
Benchmarked: full upload pipeline (parse + wiremock.zip + stub-engine.zip, 84 synthetic captures matching a real reported scale) — 0.49s end to end via the real API. Could not reproduce 40s at any tested scale; likely explanation is a first-time Maven dependency download during a separate `mvn package` step, or a stale backend process from earlier debugging.

## BUG-033 — `ingestion-service`'s separate WireMock mapping builder had no `bodyPatterns` support at all

| Field | Value |
|-------|-------|
| **ID** | BUG-033 |
| **Found** | 2026-08-27 |
| **Status** | FIXED |
| **Severity** | High |
| **File** | `services/ingestion-service/src/ingestion_service/wiremock_generator.py` |
| **Commit** | (session fix) |

**Description:**
The plain "wiremock.zip" quick-download product (built at upload time) is generated by a completely separate, independent reimplementation of WireMock mapping construction from the one the full Spring Boot project uses (`parser_worker.generator.wiremock`). This duplicate never gained `bodyPatterns`/priority/fault/delay support — so a stub with multiple scenarios recorded at the same URL (see BUG-029) got identical, unconditional request matchers in this ZIP, even after the real generator was fixed to disambiguate them. Only the first such scenario could ever actually be returned by WireMock from that specific download.

**Root cause:**
Two independent mapping-building code paths existed for what should be one source of truth; a fix to one (the real generator) never automatically applied to the other.

**Fix:**
Deleted the duplicate implementation. `generate_wiremock_zip` now calls `parser_worker.generator.wiremock.build_wiremock_mappings(parsed_file, include_lookup_table_stubs=True)` directly. The new `include_lookup_table_stubs` parameter exists because this product has no Java extension to hand a high-variant stub off to (see BUG-032/dynamic lookup-table engine in `docs/FEATURES.md`) — unlike the full Spring Boot project, it must always emit static mappings regardless of the lookup-table threshold. Added regression tests proving same-URL scenarios get distinct `bodyPatterns` in this ZIP, and that a high-variant stub still gets N static mappings here even though the full project would switch it to the lookup engine.

## BUG-032 — CA LISA inline (unlabelled) variant only ever parsed the first request/response marker in a file

| Field | Value |
|-------|-------|
| **ID** | BUG-032 |
| **Found** | 2026-08-27 |
| **Status** | FIXED |
| **Severity** | High |
| **File** | `services/parser-worker/src/parser_worker/parsers/ca_lisa_parser.py` |
| **Commit** | (session fix) |

**Description:**
The labelled CA LISA variant (explicit `RequestHeader:`/`ResponseHeader:` sections) had already been fixed to handle multiple same-URL captures in one file (BUG-029). The inline (unlabelled) variant — used by ESP-style captures with no section labels — had not: `_parse_inline_content` located only the single earliest response marker (`min(candidates)`) and parsed exactly one request block and one response block from the whole file. Any additional captures recorded after the first were either silently dropped or garbled into the first capture's "body" as raw, un-parsed text.

**Root cause:**
The inline variant predated the same-URL multi-capture work and was never revisited when the labelled variant gained it — two structural variants, only one of which handled the general case.

**Fix:**
Unified both variants through one shared pipeline: `_scan_labelled_captures`/`_scan_inline_captures` each extract every request/response marker in document order into a common `_Capture` record shape, and both feed the same `_build_stub_from_captures`, which does pairing, header-stability filtering, and same-URL differentiation identically regardless of which structural variant produced the captures. Added `TestInlineVariantMultiCaptureSameUrl` covering XML and JSON inline multi-capture files, plus a regression test confirming the original single-capture ESP shape is unaffected.

## BUG-031 — New inline-variant capture scanner: bare response marker re-matched its own tail, truncating segments

| Field | Value |
|-------|-------|
| **ID** | BUG-031 |
| **Found** | 2026-08-27 |
| **Status** | FIXED |
| **Severity** | High (caught before merge, via test suite) |
| **File** | `services/parser-worker/src/parser_worker/parsers/ca_lisa_parser.py` |
| **Commit** | (session fix) |

**Description:**
Found while writing BUG-032's fix. The new `_scan_inline_captures`, when searching for the *next* marker after a `ResponseHeader={StatusCode=...}` match, searched from `marker.start() + 1`. `_BARE_RESPONSE_RE` (`={StatusCode="`) matches the tail of that same `ResponseHeader={StatusCode=` text (which starts well after `start() + 1`), so it was found again as a spurious *second* marker — truncating the response segment right after the literal word "ResponseHeader", well before its actual header block or body. Every existing inline-variant test failed immediately (`ValueError: expected 'ResponseHeader={' or a bare '={StatusCode=' at start`).

**Root cause:**
Resuming the "find next marker" search from `match.start() + 1` doesn't skip past the matched marker text itself, so a shorter overlapping pattern (`_BARE_RESPONSE_RE`) can re-match inside a longer one (`_INLINE_RESPONSE_RE`) that was just found.

**Fix:**
Track each marker's `match.end()` and resume the next search from there instead of `start() + 1`, so a pattern can never re-match text that was part of the marker just consumed. Caught immediately by the existing 616-test suite (24 failures) before this reached any commit.

## BUG-030 — Correlation/trace headers baked into required-match headers for multi-capture CA LISA stubs

| Field | Value |
|-------|-------|
| **ID** | BUG-030 |
| **Found** | 2026-08-26 |
| **Status** | FIXED |
| **Severity** | Critical |
| **File** | `services/parser-worker/src/parser_worker/parsers/ca_lisa_parser.py` |
| **Commit** | 9495496 |

**Description:**
When a CA LISA operation was recorded multiple times (same URL, different payload per capture — see BUG-029), the resulting WireMock mapping's required headers included whichever value happened to be captured for headers like `x-requestid` and `traceparent`. Those are correlation/trace IDs that change on every real call by design — a stub requiring an exact match on one specific captured GUID would never match a real replay request, making the entire stub unusable in practice despite "succeeding" at generation time.

**Root cause:**
Required-header selection used the first capture's headers unconditionally, with no check for whether a header's value was actually stable across the operation's other captures.

**Fix:**
When a stub has more than one capture, only headers whose value is identical across **every** capture become required-match headers — computed by comparing header dicts across all captures, with no hardcoded list of "known volatile" header names. Verified live: a generated stub matched a real HTTP request using a brand-new, never-captured `x-requestid`.

## BUG-029 — Multiple same-URL CA LISA captures collided into one always-matched WireMock mapping

| Field | Value |
|-------|-------|
| **ID** | BUG-029 |
| **Found** | 2026-08-26 |
| **Status** | FIXED |
| **Severity** | Critical |
| **File** | `services/parser-worker/src/parser_worker/parsers/ca_lisa_parser.py` |
| **Commit** | 9495496 |

**Description:**
A CA LISA file recording the same operation multiple times (identical URL/method/headers, different request body per call — e.g. one customer per capture) produced only one `MatchType.ALWAYS` WireMock scenario per stub. Every capture after the first was either overwritten or simply never reachable — WireMock can only ever return the highest-priority mapping when nothing distinguishes competing ones.

**Root cause:**
The parser had no concept of "multiple captures of the same operation" — it built exactly one scenario from whichever request/response pair it found, matching on method+URL+headers alone.

**Fix:**
Added `_differentiate_bodies`: given N request bodies for the same operation, find a body field (an XML leaf element via local-name, or a top-level JSON scalar) whose value differs across every capture, and build a WireMock `bodyPatterns` matcher (`matchesXPath`/`matchesJsonPath`) per scenario — the same manual pattern used earlier to fix one-off same-URL SOAP mapping collisions, now automatic. Falls back to `MatchType.ALWAYS` only when no single field reliably distinguishes every capture (a known, accepted limitation for that edge case, not a silent wrong answer). This became the foundation for the dynamic lookup-table engine added the next day — see `docs/FEATURES.md`.

## BUG-028 — ZIP upload classified request/response files by filename before content

| Field | Value |
|-------|-------|
| **ID** | BUG-028 |
| **Found** | 2026-08-26 |
| **Status** | FIXED |
| **Severity** | High |
| **File** | `services/parser-worker/src/parser_worker/detector.py`, `portal/src/lib/httpCapturePairing.ts` |
| **Commit** | 9495496 |

**Description:**
Batch-uploading two real files produced zero stubs. One file, `AccountInstructionsPost_Response.txt` at the time of the fix (originally exported/named `..._Request.txt` by the capture tool), contained pure response data (`ResponseHeader=`/`StatusCode=`) but its filename contained "Request". `_detect_and_parse_zip`'s classifier checked filename substring match *before* content, so both files in the pair landed in the "request" bucket and the ZIP handler reported "No response files found."

**Root cause:**
A CA LISA / RTWS export tool does not always name a file consistently with what it actually contains — filename-first classification trusted a signal that was, in this real case, simply wrong.

**Fix:**
Both `detector.py`'s ZIP classifier and the portal's client-side `httpCapturePairing.ts` (kept in lockstep with the Python pairing logic) now check content first — an unambiguous `={Method=` or `={StatusCode=` marker, searched independently of any label text — and fall back to filename substring matching only when content is ambiguous (both or neither marker present). The portal fix required plumbing each batch file's text content into the pairing call (previously synchronous and filename-only); reads now happen once via a `useEffect` when the file list changes.

## BUG-027 — Custom/prefixed CA LISA section labels not recognised (exact-text-only label matching)

| Field | Value |
|-------|-------|
| **ID** | BUG-027 |
| **Found** | 2026-08-26 |
| **Status** | FIXED |
| **Severity** | Critical |
| **File** | `services/parser-worker/src/parser_worker/parsers/ca_lisa_parser.py` |
| **Commit** | 9495496 |

**Description:**
A real capture file used `AccountInstructionsRequestHeader:` / `AccountInstructionsResponseHeader:` instead of the bare `RequestHeader:`/`ResponseHeader:` labels the parser expected. `_detect_variant` misclassified the file as the "inline" (unlabelled) structural variant, and the mismatched downstream parsing garbled the request/response boundary entirely.

**Root cause:**
`_LABELLED_REQUEST_LABEL_RE`/`_LABELLED_RESPONSE_LABEL_RE` were exact-text regexes (`^RequestHeader:$`, `^ResponseHeader:$`) — any tool-specific label customisation (or a different export tool's naming convention entirely, e.g. Postman/Bruno-style exports) fell straight through to the wrong code path.

**Fix:**
Replaced exact-text label matching with structural detection: a label line's role (request-header / response-header / body) is now decided purely by what immediately follows it — a `={Method=` block, a `={StatusCode=` block, or plain body content — never by the label's literal wording. This is label-naming-agnostic by construction, not just patched for this one prefix, so it survives whatever convention a future export tool or hand-authored file happens to use for the same underlying shape.

## BUG-026 — SOAP WS-Security enforcement completely non-functional

| Field | Value |
|-------|-------|
| **ID** | BUG-026 |
| **Found** | 2026-08-26 |
| **Status** | FIXED |
| **Severity** | Critical |
| **File** | `services/parser-worker/src/parser_worker/templates/stub-engine/src/main/java/com/mockingbird/stubs/` |
| **Commit** | dc033b5 |

**Description:**
Enabling WS-Security (`mockingbird.soap.ws-security.enabled=true`) had no effect: a SOAP request with zero WS-Security header still received a normal 200 response from the stub.

**Root cause:**
Enforcement was implemented as a Spring-WS `EndpointInterceptor` (`WsSecurityConfig.java`, since deleted). SOAP stub traffic is served entirely by WireMock's own embedded server (port 8080) — a completely separate HTTP stack from Spring-WS's dispatcher (port 8081, used only for WSDL/actuator). The interceptor never saw stub calls at all.

**Fix:**
Rebuilt as `WsSecurityRequestFilter`, a `StubRequestFilterV2` registered directly into `WireMockConfiguration.extensions(...)` — the same request pipeline that actually serves stub traffic. Validates a plain-text `UsernameToken` (namespace-aware, so any WS-Security prefix works) and rejects with a SOAP Fault before WireMock's own matching runs. This is also the mechanism `DynamicLookupRequestFilter` (the lookup-table engine, see `docs/FEATURES.md`) was later built on.

## BUG-024 — CA LISA sibling `httpDetails` block silently swallowed into request body

| Field | Value |
|-------|-------|
| **ID** | BUG-024 |
| **Found** | 2026-08-26 |
| **Status** | FIXED |
| **Severity** | High |
| **File** | `services/parser-worker/src/parser_worker/parsers/ca_lisa_parser.py` |
| **Commit** | 1b59723 |

**Description:**
Some manually-reformatted SOAP/XML captures close the outer `={...}` block early (right after `URL=`) and emit `httpDetails={...}` (and therefore `httpHeaders`/`SOAPAction`) as a separate sibling block afterwards, instead of nesting it inside. Without special handling, `_find_block_end`'s first match ends the header block before that sibling appears, so it — and headers like `SOAPAction`, often the only thing distinguishing SOAP operations sharing one URL — got silently absorbed into what looked like the request body.

**Root cause:**
The parser assumed one well-formed nested block per capture; this capture layout is a real, observed structural variant that isn't.

**Fix:**
Added `_consume_sibling_kv`, which absorbs additional top-level `Key="value"` / `Key={...}` tokens appearing immediately after an already-closed block, merging them into the same parsed header dict, before body extraction begins.

## BUG-023 — WireMock `Content-Type` header matched case-sensitively, breaking real requests

| Field | Value |
|-------|-------|
| **ID** | BUG-023 |
| **Found** | 2026-08-26 |
| **Status** | FIXED |
| **Severity** | High |
| **File** | `services/parser-worker/src/parser_worker/generator/wiremock.py` |
| **Commit** | 1b59723 |

**Description:**
A generated mapping's `Content-Type` header matcher used a verbatim-captured value (e.g. `charset=utf-8`) and never matched real live traffic, regardless of the case the client actually sent.

**Root cause:**
Found by loading a captured mapping into a real running WireMock instance and sending real requests: Jetty (WireMock's underlying HTTP server) normalises the `Content-Type` charset parameter's casing before the request ever reaches WireMock's matcher, but the stored matcher compared against the exact captured casing.

**Fix:**
`Content-Type` header matchers are now built with `"caseInsensitive": true`; all other headers stay case-exact, since a case mismatch there carries real distinguishing meaning.

## BUG-022 — WireMock query parameters not URL-decoded before storing as a matcher

| Field | Value |
|-------|-------|
| **ID** | BUG-022 |
| **Found** | 2026-08-26 |
| **Status** | FIXED |
| **Severity** | High |
| **File** | `services/parser-worker/src/parser_worker/generator/wiremock.py` |
| **Commit** | 1b59723 |

**Description:**
A captured query string like `?aggregate=SUP+FLAGS` produced a matcher requiring the literal text `SUP+FLAGS` — a real request's query string arrives already decoded by the client/browser (`+` → space), so the matcher never matched.

**Root cause:**
WireMock decodes incoming query strings (`application/x-www-form-urlencoded` rules: `+` → space, `%XX` → byte) before matching `queryParameters`. The stored matcher was built from the raw, still-encoded captured text.

**Fix:**
Query parameter keys/values are decoded with `unquote_plus` before being stored as `equalTo` matchers, so the matcher compares against what WireMock will actually see. Verified by loading a generated mapping into a real WireMock instance.

## BUG-008 — `Set-Content -Encoding UTF8` writes UTF-8 BOM, causing CA LISA parse failure

| Field | Value |
|-------|-------|
| **ID** | BUG-008 |
| **Found** | 2026-06-22 |
| **Status** | FIXED |
| **Severity** | High |
| **File** | `Sample_SV_Files/ESP/combined_request_response.txt` |
| **Commit** | 5f57c94 |

**Description:**  
The combined CA LISA request+response file always failed validation with `Parse error: ESP request: expected '{' after '='`. First bytes were `0xEF 0xBB 0xBF` (UTF-8 BOM) instead of `0x3D 0x7B` (`={`).

**Root cause:**  
PowerShell 5.1 `Set-Content -Encoding UTF8` and `[System.IO.File]::WriteAllText(path, content, [System.Text.Encoding]::UTF8)` both write a UTF-8 BOM. **Fix:**  
Used `[System.IO.File]::WriteAllBytes` with raw `Uint8Array` concatenation (request bytes + `0x0A` newline + response bytes) to produce a BOM-free binary file. Verified first bytes are `0x3D 0x7B` (`={`).

## BUG-003 — CA LISA ZIP pairing: `else: continue` blocked fallback from timestamp → prefix strategy

| Field | Value |
|-------|-------|
| **ID** | BUG-003 |
| **Found** | 2026-06-21 |
| **Status** | FIXED |
| **Severity** | High |
| **File** | `services/parser-worker/src/parser_worker/detector.py` |
| **Commit** | 1d4dac0 |

**Description:**  
When parsing a ZIP archive with ESP-format CA LISA files, only 1 stub was returned instead of 2. The ESP files have timestamps that differ by 1 second between request (`_100912`) and response (`_100911`). Strategy 1 (exact timestamp match) found the timestamp in the request filename but found no response with the same timestamp, then hit `else: continue` (Python for-else on the response loop), which jumped to the next request and never tried Strategy 2 (longest common prefix).

**Root cause:**  
`for response in responses: ... else: continue` is Python's for-else pattern — the `else` runs when the loop finishes WITHOUT a `break`. Combined with `continue` at the outer level, it completely skipped prefix matching when timestamp matching produced no hit.

**Fix:**  
Replaced the for-else pattern with a `matched = False` flag. Strategy 2 (prefix matching) now always runs as fallback when Strategy 1 produces no match.

## BUG-002 — CA LISA Wealth format: brace-counting consumed request body as header block

| Field | Value |
|-------|-------|
| **ID** | BUG-002 |
| **Found** | 2026-06-21 |
| **Status** | FIXED |
| **Severity** | Critical |
| **File** | `services/parser-worker/src/parser_worker/parsers/ca_lisa_parser.py` |
| **Commit** | 1d4dac0 |

**Description:**  
The Wealth variant was parsed with method `GET` instead of `POST`. The request body was silently lost. The `_extract_wealth_section` function used brace-depth counting to find the end of the `={Method="POST" ...}` block, but the outer `={...}` block in Wealth files is **never properly closed** (the closing `}` is absent). Brace counting ran past the entire request block, consuming the JSON body as "header block text". Then `_parse_kvblock` received the JSON body starting with `{` as if it were a nested block and misread `{Method` as the key name instead of `Method`. `result.get("Method", "GET")` returned the default.

**Root cause:**  
CA LISA Wealth format has a structural quirk: the outer `={...}` key=value block is always missing its closing `}`. Brace counting is not a valid parsing strategy for this format.

**Fix (two-part):**
1. Rewrote `_extract_wealth_section` to use the section label (`Request:` / `Response:`) as a hard block boundary instead of brace counting.
2. Changed `_parse_kvblock` to use `_find_block_end()` (which handles quoted strings correctly) to detect whether `{...}` is properly closed; if unclosed, strips just the leading `{` without requiring a matching `}`.
